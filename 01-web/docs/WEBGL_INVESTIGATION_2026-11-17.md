# 3D表示の初期化失敗：調査記録（2026-11-17）

## 現在の結論

ユーザー環境で「3D表示に対応したブラウザでお楽しみください。」となった**根本原因は未特定**です。プレビュー起動後にも同じ文言が出るとの回答を受け、WebGL2初期化の失敗を確認しました。テスト用Chromiumで成功したことはユーザーのブラウザでの成功を意味しません。

その後、失敗時だけの起動設定の再試行と、セーブ情報を含めず自動送信もしない診断画面を追加しました。追加対応と再検証は後半に記載しています。ブラウザ側がWebGL2自体を利用できない場合まで解決したわけではありません。

## 初回調査（21121da時点）

元のアプリケーションは Web 2.29（296種・14展示室）、取り込みコミットは `5bee06c15ad99ea88be1cc358dc625f95bd99c1d`。初回の `21121da` は再現・回帰テストとこの記録の追加だけであり、その時点では描画品質・種ID・個体・保存処理・初期化設定を変更していません。以下は引き継ぎメモの過去の結果ではなく、この checkout で初回に実施した確認です。

### 初回にソースで確認したこと

- `aquarium-scene.js` の `AquariumScene` コンストラクタが `THREE.WebGLRenderer` の例外を捕捉し、`renderer=null` にします。`attach()` はこの状態で件の文言を表示します。
- この文言だけでは、ブラウザの非対応、GPU・ドライバ設定、コンテキスト資源不足などの原因を区別できません。捕捉した例外の詳細はアプリの画面や診断APIには保存されていません。
- 利用する Three.js は WebGL2 の描画経路です。水槽と探索は同じ canvas / renderer を共有します。
- 初期化済みのコンテキスト消失と、コンストラクタでの初期化失敗は別の事象です。前者だけを再現しても、後者の根本原因を証明したことにはなりません。

## 隔離ブラウザで確認したこと

環境：Linux、Node.js 22.22.3、lockfile の Playwright / Three.js、Chromium 153.0.8010.0、ANGLE / SwiftShader（ソフトウェア描画）。ブラウザ実行ファイルと不足する共有ライブラリは一時ディレクトリに用意し、リポジトリの依存関係や OS の設定は変更していません。ソフトウェア描画用の起動オプションは試験用であり、ユーザーのブラウザ設定変更を推奨するものではありません。

新規テスト `tests/current/webgl-lifecycle.e2e.cjs` で次を確認しました。

1. 14展示室すべてで WebGL2 が使用でき、キャンバスに非透明ピクセルがあること。
2. 展示室間、および探索・水槽間の反復移動で同じ canvas を使い続け、自然なコンテキスト消失がないこと。
3. 探索の「動きを減らす」の切り替え後、描画ループが停止・再開すること。
4. `WEBGL_lose_context` による水槽のコンテキスト消失・復元後、再び描画されること。
5. 通常の同一オリジン iframe 内でも描画できること。**元のプレビューホスト・埋め込み条件そのものの再現ではありません。**
6. canvas の WebGL コンテキスト生成を試験で拒否すると、件の文言が再現すること。その状態でも画面移動と探索の静止画フォールバックが動くこと。
7. 上記の画面移動・復旧・フォールバックで、合成個体のID・種・名前・サイズ・育成度を失わず、未処理のページ例外が発生しないこと。

通常の開発環境では、`01-web/` で次のように実行します。

```sh
npm ci
npx playwright install chromium
npm run build
npm run test:webgl
```

試験は一時ポートの静的HTTPサーバー、新しいブラウザコンテキスト、合成セーブを使い、`**/__yoru/preview-save` を遮断します。ポート3000の本番プレビューや既存 `preview-data/` を使用しません。

### 別途試した旧E2Eの不成立

`node tests/current/voxel-journey.e2e.cjs` は、描画の前に `E.startExplore(s, 'reef', now)` のアサーションで失敗しました。この旧テストは `reef` / `cold-sea` / `fresh` を探索先としており、現行の6分類と一致しません。今回の「3D表示」問題が再現した結果ではありません。この旧スイート自体は修正していません。新規WebGLテストでは現行の `coastal` を使って共有描画・画面往復等を検証しています。

したがって、**全E2Eファイルが成功したという報告ではありません。** また、ソフトウェア描画での成功は実機GPU・Safari・Android・元のプレビュー環境での正常動作を保証しません。

## 追加対応：プレビューでの再報告後

### 実装

- `webgl-renderer.js` で WebGL2 を明示的に取得し、同じ設定を Three.js に渡します。成功後は従来どおり水槽・探索で1つの renderer / canvas を共有します。
- 既存の高品質設定（`high-performance`、アンチエイリアスあり）を最初に試します。失敗時だけ、GPUをブラウザに任せる同品質設定を試し、それも失敗した場合だけアンチエイリアスを無効にして最大3回で終了します。形・モデル・ライト・種ID・個体・保存処理は変更していません。通常の環境で画質を下げる処理ではありません。
- 各試行には新しいcanvasを使います。Three.jsの初期化途中で失敗して残ったコンテキストは解放し、成功したコンテキストは解放しません。画像共有用の `preserveDrawingBuffer` はすべての設定で維持します。
- `webglcontextcreationerror.statusMessage` と例外メッセージを保持します。失敗画面と「設定 → 3D表示 → 診断を見る」から確認でき、ブラウザ・埋め込みの別・試行した設定・失敗理由を表示します。診断情報をサーバーへ自動送信せず、セーブ内容やURLを明示的に収集しません。
- ブラウザのエラーメッセージはHTMLとして実行されないようエスケープして表示します。
- 誤解を招く非対応の断定を「3D表示を開始できませんでした」に変更しました。診断画面に同じURLを別タブで開くリンクを設けていますが、別タブなら必ず直るという説明はしていません。

### 追加対応後の再検証

依然として Linux / Chromium / SwiftShader の隔離試験であり、ユーザー端末のGPUや元の埋め込み条件そのものの検証ではありません。

| 確認 | 結果 |
| --- | --- |
| `npm test` | 117 / 117 成功（起動・診断の7件を追加） |
| `npm run build` | 別の隔離コピーで成功 |
| `webgl-startup.e2e.cjs` | 通常、GPU指定拒否、アンチエイリアス拒否、全設定拒否の4経路が成功 |
| `webgl-lifecycle.e2e.cjs` | 全14室、共有canvas、探索往復、コンテキスト復旧、iframe、失敗表示が成功 |
| `npm run test:e2e` | 既定の2スイートが成功 |
| `npm run test:backup` | 一時保存先で復元・競合・破損保護などが成功 |

起動E2Eでは正常時・代替設定の実際の非透明ピクセルとPNG画像書き出し、全失敗時の診断表示を検証しました。エラーにHTML文字列を混ぜても実行されないこと、320px画面での収まり、個体のID・種・名前・サイズ・育成度の保持も確認しました。`npm run test:webgl` は起動E2EとライフサイクルE2Eの両方を実行します。

試験は一時ポート・新規ブラウザコンテキスト・合成保存に限定し、実プレビューの保存APIは使用していません。元のプレイヤーのセーブの移行やサイトデータの削除も行っていません。

## 次の切り分けに必要な情報

- 発生した端末・OSとブラウザ名、分かればバージョン。
- プレビュー埋め込み内／別タブ／単体HTML／公開サイトのどこで開いたか。
- 最初から全水槽で出るか、探索から戻った後・バックグラウンド復帰後など特定の操作で出るか。

修正したプレビューを通常の再読み込みで開き直し、まだ表示できない場合は「3D表示の診断を見る」のテキストを確認します。それをWebGL2初期化時のブラウザ側エラーとして照合する必要があります。ユーザー環境の成功確認前に解決済みとはしません。通常設定の画質は維持し、セーブの初期化・サイトデータやキャッシュの削除を行わない方針です。
